# Spring Boot Logging & Metrics

## Introduction

Logging and metrics are essential for understanding an application's behavior and performance.

They help with:

- Monitoring applications
- Troubleshooting issues
- Diagnosing problems
- Understanding application performance
- Optimizing application behavior

## Logging vs Metrics

| Logging | Metrics |
|---|---|
| Records events, actions, and information | Measures application/system behavior |
| Useful for troubleshooting and auditing | Useful for monitoring and performance analysis |
| Provides detailed information about what happened | Provides quantitative measurements |

### Quick Recall

> **Logging tells us what happened. Metrics tell us how the application is performing.**

---

## 2. Logging Fundamentals

**Logging** is the process of recording events, actions, and information generated by an application.

Logs are useful for:

- Monitoring application behavior
- Troubleshooting problems
- Auditing application activity
- Understanding what happened during application execution

### Common Logging Concepts

- **Log Level** → indicates the severity or importance of a logged event.
- **Log Message** → the information recorded in the log.
- **Log Pattern** → defines how log information is formatted and displayed.

Common logging frameworks and APIs used in Java applications include:

- **SLF4J**
- **Logback**
- **Log4j2**

---

## Logging Levels

Logging levels indicate the **severity of an event**.

From highest severity to lowest:

```text
ERROR
  ↓
WARN
  ↓
INFO
  ↓
DEBUG
  ↓
TRACE
```

### ERROR

Indicates a serious problem or failure that may prevent an operation from completing successfully.

### WARN

Indicates a potentially problematic situation that does not necessarily stop the application.

### INFO

Provides general information about the normal operation of the application.

### DEBUG

Provides detailed information useful for debugging and understanding application behavior during development.

### TRACE

Provides the most detailed level of logging information and is useful when very fine-grained execution details are required.

> **Quick Recall:**
>
> `ERROR → WARN → INFO → DEBUG → TRACE`
>
> Higher level → greater severity  
> Lower level → more detailed information

---

## Spring Boot Logging with SLF4J

Spring Boot applications can use **SLF4J** to create and work with loggers.

A logger can be created using `LoggerFactory`:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class SampleClass {

    private static final Logger logger =
        LoggerFactory.getLogger(SampleClass.class);

    public void performActions() {
        logger.debug("This is a debug message.");
        logger.info("This is an info message.");
        logger.warn("This is a warning message.");
        logger.error("This is an error message.");
    }
}
```

### Understanding the Implementation

**`Logger`**

Represents the logger used to write log messages.

**`LoggerFactory`**

Creates a logger for the specified class.

```java
LoggerFactory.getLogger(SampleClass.class);
```

**Logging methods**

```text
logger.debug() → Debug information

logger.info()  → General application information

logger.warn()  → Warning information

logger.error() → Error information
```

> **Quick Recall:**
>
> `LoggerFactory` → creates the logger  
> `Logger` → records log messages  
> `debug / info / warn / error` → log at different levels

## Logging Configuration with `application.yml`

Spring Boot allows logging levels to be configured through the `application.yml` file.

```yaml
logging:
  level:
    root: WARN
    com.example.packageName: DEBUG
```

### Understanding the Configuration

- **`logging.level.root: WARN`** → sets the root logger's level to `WARN`.
- **`com.example.packageName: DEBUG`** → sets the logging level for the specified package to `DEBUG`.

### Logging Level Behavior

When the logging level is set to `WARN`, messages at `WARN` and `ERROR` levels are enabled, while lower-severity levels such as `INFO`, `DEBUG`, and `TRACE` are filtered out.

A package configured with `DEBUG` can produce more detailed logs than the root logger.

> **Quick Recall:**
>
> `root` → configures the default logging level.
>
> A package-specific level → configures logging for that package.

## Logging Colors

Spring Boot console logs can use different colors to help distinguish logging levels.

The course notes describe the following color associations:

| Logging Level | Color |
|---|---|
| `INFO` | White / Green |
| `DEBUG` | Blue / Cyan |
| `WARN` | Yellow / Orange |
| `ERROR` | Red |
| `TRACE` | Gray / Light Blue |

### Enabling ANSI Colors

Add the following configuration to `application.yml`:

```yaml
spring:
  output:
    ansi:
      enabled: ALWAYS
```

This setting enables ANSI color output in the console.

> **Quick Recall:**  
> ANSI configuration controls colored console output, making log levels easier to distinguish visually.

## Saving Logs to a File

Instead of displaying logs only in the console, Spring Boot can also write log messages to a file.

Configure the file name in `application.yml`:

```yaml
logging:
  file:
    name: application.log
```

This configuration directs logging output to `application.log`.

### Log Management

When saving logs to files, consider:

- **Log Rotation** → manages log files as they grow.
- **Retention Policies** → determine how long log files are kept.
- **File Location** → specifies where log files are stored.

> **Quick Recall:**
>
> `logging.file.name` → configures the log file name.
>
> Log rotation and retention policies help manage stored logs.

## Metrics Fundamentals

Metrics are **quantitative measurements** used to understand application and system behavior.

They help monitor performance, identify issues, and evaluate application health.

### Types of Metrics

#### 1. Application Metrics

Measure the behavior and performance of an application.

Examples:
- Request count
- Response times
- Error rates

#### 2. System Metrics

Measure the resources and activity of the underlying system.

Examples:
- CPU usage
- Memory usage
- Disk I/O
- Network traffic

#### 3. Business Metrics

Measure application-specific business goals and outcomes.

Examples:
- User engagement
- Sales
- Custom Key Performance Indicators (KPIs)

### Quick Recall

| Metric Type | Focus | Examples |
|---|---|---|
| Application | Application behavior | Requests, response times, errors |
| System | System resources | CPU, memory, disk I/O, network |
| Business | Business outcomes | Engagement, sales, KPIs |

> **Remember:** Application metrics measure application behavior, system metrics measure resource usage, and business metrics measure business outcomes.

## Micrometer

**Micrometer** is a Java library used to collect, aggregate, and export application metrics to monitoring systems.

It acts as a bridge between an application and monitoring tools such as **Prometheus** and **Grafana**.

### Adding the Prometheus Registry Dependency

To integrate Micrometer metrics with Prometheus, add the following dependency to the project's `pom.xml`:

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
    <scope>runtime</scope>
</dependency>
```

### Quick Recall

- **Micrometer** → collects and exposes application metrics.
- **Prometheus registry** → enables metrics integration with Prometheus.
- **Monitoring systems** → receive metrics for monitoring and analysis.

## Prometheus

**Prometheus** is an open-source monitoring and alerting system used to collect and analyze metrics.

It stores metrics as **time-series data**, allowing application and system behavior to be monitored over time.

### Key Features

- **Time-Series Database** → stores metric measurements over time.
- **Data Scraping** → collects metrics from configured targets at regular intervals.
- **Alerting** → supports alerts based on defined conditions.
- **Reliability** → designed to provide reliable monitoring.

### Role in Application Monitoring

Prometheus collects metrics exposed by applications and makes the data available for monitoring and analysis.

```text
Spring Boot Application
          ↓
   Micrometer Registry
          ↓
      Prometheus
          ↓
   Metrics Monitoring
```

> **Quick Recall:**
>
> Prometheus → collects and stores time-series metrics, supports monitoring, and provides alerting capabilities.

## Grafana

**Grafana** is an open-source monitoring and visualization platform used to analyze and visualize application and system metrics.

### Key Features

- **Dashboards** → display metrics through customizable dashboards.
- **Data Sources** → supports Prometheus, InfluxDB, Elasticsearch, and relational databases.
- **Alerting** → helps monitor metrics and identify issues.
- **Visualization** → presents metrics in graphs and other visual formats.
- **Plugins** → extends functionality through additional integrations.
- **Collaboration** → supports sharing dashboards and monitoring insights.

### Prometheus and Grafana

Prometheus collects and stores metrics, while Grafana visualizes those metrics through dashboards.

> **Quick Recall:**
>
> Prometheus → collects and stores metrics.
>
> Grafana → visualizes metrics and creates monitoring dashboards.

## Docker Fundamentals

**Docker** is a platform for packaging applications and their dependencies into portable containers. Containers provide an isolated environment for running applications.

### Key Concepts

- **Docker Engine** → runs and manages Docker containers.
- **Docker Daemon** → manages Docker objects such as images, containers, networks, and volumes.
- **Docker CLI** → lets users interact with Docker through commands.
- **Docker Image** → a template used to create containers.
- **Docker Container** → a running instance of an image.
- **Dockerfile** → contains instructions for building a Docker image.
- **Docker Registry** → stores and distributes Docker images.
- **Docker Compose** → defines and runs multi-container applications using a YAML configuration file.
- **Volumes** → persist data beyond a container's lifecycle.
- **Networking** → enables communication between containers and other systems.

### Docker in Application Monitoring

Docker can run monitoring tools such as Prometheus and Grafana in separate containers. Docker Compose can define both services and their configurations in one file.

> **Quick Recall:**
>
> Image → template for creating a container.
>
> Container → isolated runtime instance of an image.
>
> Docker Compose → manages multi-container applications.

## Running Prometheus and Grafana with Docker Compose

**Docker Compose** allows Prometheus and Grafana to run as separate services defined in a single YAML file.

### `docker-compose.yml`

```yaml
version: '3.7'

services:
  prometheus:
    image: prom/prometheus:v2.44.0
    container_name: prometheus
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml

  grafana:
    image: grafana/grafana:9.5.2
    container_name: grafana
    ports:
      - "3000:3000"
    restart: unless-stopped
    volumes:
      - ./grafana/provisioning/datasources:/etc/grafana/provisioning/datasources
```

### Configuration Overview

- **Image** → specifies the image used to create each container.
- **Ports** → exposes Prometheus on port `9090` and Grafana on port `3000`.
- **Volumes** → mounts local configuration files or directories into the containers.
- **Restart policy** → `unless-stopped` allows Grafana to restart unless it has been explicitly stopped.

### Start the Services

Run the following command from the directory containing `docker-compose.yml`:

```bash
docker compose up
```

This starts the services defined in the Compose file.

> **Quick Recall:** Docker Compose defines multiple services in YAML, while `docker compose up` starts them.

## Prometheus and Grafana Configuration

### Prometheus Configuration — `prometheus.yml`

Prometheus uses `scrape_configs` to define which targets it collects metrics from and how frequently it collects them.

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:

scrape_configs:
  - job_name: 'prometheus'
    scrape_interval: 5s
    static_configs:
      - targets: ['127.0.0.1:9090']

  - job_name: 'my-spring-actuator'
    metrics_path: '/actuator/prometheus'
    scrape_interval: 2s
    static_configs:
      - targets: ['192.168.0.110:8081']
    labels:
      application: "Ninjas Social Media Application"
```

**Key properties:**

- `scrape_interval` → defines how frequently metrics are collected.
- `evaluation_interval` → defines how frequently alerting and recording rules are evaluated.
- `job_name` → identifies a group of scrape targets.
- `metrics_path` → specifies the endpoint from which metrics are collected.
- `static_configs` → defines targets explicitly.
- `labels` → attaches additional identifying information to scraped metrics.

### Grafana Data Source — `datasources.yml`

Grafana uses a data source configuration to connect to Prometheus.

```yaml
apiVersion: 1

datasources:
  - name: Prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true
```

**Key properties:**

- `name` → data source name displayed in Grafana.
- `type` → identifies Prometheus as the data source.
- `access: proxy` → routes data requests through Grafana's server.
- `url` → specifies the Prometheus service address.
- `isDefault: true` → makes Prometheus the default data source.

> **Quick Recall:** Prometheus configuration defines where metrics are scraped from; Grafana's data source configuration defines where dashboards retrieve metrics from.

## Interview & Quick Revision

### Logging

- **Logging vs Metrics:** Logging records events; metrics measure application or system behavior quantitatively.
- **SLF4J:** Provides a logging abstraction through `Logger` and `LoggerFactory`.
- **Logging Levels:** `ERROR`, `WARN`, `INFO`, `DEBUG`, `TRACE` — ordered from highest to lowest severity.
- **Logging Configuration:** `logging.level` configures the root or package-specific logging level.
- **File Logging:** `logging.file.name` specifies the log file name.
- **ANSI Colors:** `spring.output.ansi.enabled` controls ANSI color output.

### Metrics & Monitoring

- **Micrometer:** Collects and exports application metrics through monitoring-system integrations.
- **Prometheus:** Scrapes and stores time-series metrics and supports alerting.
- **Grafana:** Visualizes metrics through dashboards and supports alerting.
- **Docker:** Packages applications and dependencies into portable containers.
- **Docker Compose:** Defines and runs multiple services using YAML configuration.

### Monitoring Flow

```text
Spring Boot Application
          ↓
Micrometer / Prometheus Registry
          ↓
      Prometheus
          ↓
       Grafana
          ↓
  Dashboards & Visualization
```

### Quick Interview Questions

1. **What is the difference between logging and metrics?**  
   Logging records events and details; metrics provide quantitative measurements.

2. **What is the role of SLF4J?**  
   It provides a common logging API that can work with different logging implementations.

3. **What is Micrometer used for?**  
   It provides an instrumentation facade for collecting and exporting application metrics.

4. **What is Prometheus responsible for?**  
   Scraping and storing metrics as time-series data and supporting alerting.

5. **Why use Grafana with Prometheus?**  
   Grafana visualizes Prometheus metrics through dashboards.

6. **What is Docker Compose used for?**  
   Defining and running multi-container applications through a YAML configuration.

> **Final Recall:** SLF4J → logging API; Micrometer → metrics instrumentation; Prometheus → metrics collection and storage; Grafana → visualization; Docker Compose → multi-service orchestration.
